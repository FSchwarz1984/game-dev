## 2. v0.1 怎么动（精确）

代码在 `legacy/v0.1/src/vista.js` L9–19、L35–59。画布在 960×540 视口下原生为 482×272（与新管线的 480×270 基本一致）。

**平原上的灯不动。** 1360 个点：

- 6 个城区按高斯分布撒点，各区数量为 420、220、200、90、110、120；
- 另有 5 条各 40 点的直线（道路）。
- 每个点 1–2 像素宽、1 像素高，深度按 `d²` 压向地平线。
- 夜里约 30% 的时间熄着（`sin(2t + 30·ph) < −0.6`），所以整片在闪。

**升起的是另一组"灯笼行列"**，共 90 个：

- 第 i 个的进度：`p = frac(i/90 + 0.018·t)`。走完全程 55.6 秒，平均每 0.62 秒出发一个。
- 一打开就整条铺满，没有"第一个出发"的过程。
- 位置：
  ```
  x = W·(0.60 − 0.20·p + 0.02·sin(3p + φ))      φ ∈ [0, 1) 每个灯笼一个
  y = 地平线 + 6 − 0.46H·p − 0.05H·sin(πp)
  ```
  - 从地平线下 6 像素（约 x=289）升到画面顶端（约 x=193）。
  - 向左倾，约偏离竖直 35–40°。
  - 中段向上弓起约 14 像素。
  - 竖直速度约 2.3 像素/秒，很慢。
- 透明度：
  ```
  clamp(6p,0,1) · clamp(3(1−p),0,1) · (0.75 + 0.25·sin(6t + 20φ))
  ```
  前 1/6 渐入，后 1/3 渐出，每个各自约 1 Hz 闪烁。
- 点的样子：1×2 像素；颜色 `#ff8a46` 与 `#ffb070` 各占一半；φ<0.3 的在上方多一个 `#ffe0b0` 的亮头。
- **没有拖尾**。合成时整体泛光（夜里阈值 0.55），所以有一层柔和的橙色光晕。

**沙漏从哪里来：横向相位只有 1 弧度宽。** φ 只取 [0,1)，而不是 [0,2π)。所以同一高度上各点的横向偏移，落在 `sin` 的一段 1 弧度宽的区间里：

- 区间跨过 `sin` 的峰顶时，所有点挤在一起，这就是"腰"，在 `p ≈ (π/2 − 0.5)/3 ≈ 0.36` 处；
- 区间在 `sin` 的陡坡上时，点被拉开。

每个点在上升途中都沿着自己的正弦横向摆动：下面的点先向腰部"聚拢"，过了腰又各自散开。

实测的长曝光宽度：

| 位置 | 宽度 |
|---|---|
| 底部（约 y=121） | 约 9 像素 |
| 约 40% 高处（y≈77） | 收到约 4 像素 |
| 上部（y≈55 / 33） | 放宽到 8 / 11 像素以上 |
| 再往上 | 渐出 |

整条流每一行只有一道，不分叉。这就是"点点聚集、像倒置的沙漏往上流"：宽 → 窄 → 宽，点在流动中先聚后散，而且始终是一颗颗分开的点。

## 3. 第一段（HEAD）怎么动

代码在 `src/vista/south.js` L106–219、L471–562，`src/vista/lights.js`。

- **10 条左右的"行列"**：头人家、河岸篝火、两片稻田的倒影、城镇，以及两侧的村落（L141–158）。每个地方各有一条固定的 S 形折线（L159–183），汇入城镇上空的一根光柱，光柱通向天门。
- 每条行列**按固定间隔**每 1.25 秒放出一盏灯（以 30 秒走完 `rise` 计，L623）。所有灯以 6.5 像素/秒沿**同一条折线**走，横向只摆 ±0.4 像素（L509）。
- 每盏灯：
  - 2×2 的核，半径 5 的光晕，**后面拖着两段 2 像素的尾巴**（L529–546）；
  - 越往上越从琥珀色变成远岸的淡青色。
- 光柱：一道竖直的淡光（L548–562）。
- 两盏"独行"的灯先走。地面上每个地方的灯从边缘向中心依次熄灭。
- **实测长曝光**：中段每一行都有 6–9 道分开的轨迹。画面上是一束束像珠串一样等距排开的弧线，从两侧对称地汇入中央的光柱（按序章节奏回放，在 t=20–23 秒时最明显）。

**为什么读起来是"连成线、有序"**：

1. 同一地方的灯走完全相同的路；
2. 间隔恒定；
3. 拖尾把相邻的灯连了起来；
4. 左右对称的分道；
5. 最后还有一根竖直的光柱。

这五条每一条都在制造"线"。

## 4. 目标版本 `8196ebf`：升灯的运动模型（新引擎照此移植）

- 平原上的**每一盏灯**（窗、灯笼、篝火、稻田倒影）都沿**自己的三次贝塞尔曲线**升向天门口（`south.js@8196ebf` L106–160、L479–520）。
- 控制点：
  - 先到所在地方正上方的一个聚集点；
  - 再按地方加 ±7/±5 像素的偏移；
  - 终点在门口 ±1.5 像素。
- 每盏灯升 7.2–9.9 秒，地方之间错开出发，同一地方内按随机顺序排队。
- 核 1–2 像素，光晕 2–6 像素，尾巴 1–8 像素。
- **实测长曝光**：一个从整片平原收向一点的、密实的"倒漏斗"（像一只水母）。门口附近宽约 56 像素，中段最宽约 300 像素；每行 12–18 道并在一起。
- 它不是"线"：每一行有十几道轨迹叠在一起，看起来是许多星火从四面八方聚到一点。**这就是用户要的样子。**
- 移植要点（`south.js@8196ebf`）：
  - 出发顺序：先是庄屋的一盏灯（rise 0.03），再是一处篝火（0.11），这两盏单独走、慢、尾巴长（11 秒，尾 8 节）。之后每个地方按离镇子的远近，从 rise 0.17–0.30 开始，在 0.96 之前把自己的灯一盏盏放走，地方之间同时进行。
  - 轨迹：三次贝塞尔。起点是灯的位置；第一控制点在它所在地方的中心正上方 16–34 像素（加地方偏移 ±7/±5，再加 ±1 像素抖动）；第二控制点在门口与地方中心之间（x 取 0.62 的插值，y 取门口与"地方上方 40 像素"之间 0.45 的插值）；终点是门口 ±1.5 像素。
  - 速度：7.2–9.6 秒走完；进度曲线 `s = u·0.62 + smoothstep(u)·0.38`（先匀速、最后加速收进门口）。
  - 颜色：本岸的暖色（窗、灯笼、篝火）在路程过半之后渐变成天岸的淡翡翠色。
  - 呈现：1 像素的核（篝火和最先的两盏是 2×2），2–6 像素的阶梯光晕，尾巴 1–3 节；云还没开时，快到门口的灯被云吞掉。
- 新引擎里可以提升的地方（不改变"聚向一点"的形状）：HDR 光晕、门口随抵达的灯数一亮一亮、灯离开时地面上原来的位置熄灭的过渡、更多的灯（手机降档）。

## 5. （作废）按 v0.1 写的复刻规格

> 用户已更正：目标不是 v0.1。本节保留作记录，不要实现；实现按第 4 节。

### 原文

### 5.1 必须保留的五个性质（验收标准）

1. **一股，不分道**：长曝光里任何高度的轨迹都只有一道连续的包络。最底部汇入前可以有零散的点，但不能有分开的车道。
2. **沙漏形包络**：底宽 → 腰窄 → 上宽，然后渐出。腰在全程的 30–45% 高处。v0.1 的比例是 9 : 4 : 11（像素）。
3. **点，不是线**：核 1×2 像素，**没有拖尾**（最多一帧残影）。相邻点不能用任何东西连起来。
4. **各走各的**：每个点有自己的横向相位和闪烁相位。路径不共用，速度可以有 ±15% 的差别，所以点会互相超过、交错。
5. **慢**：竖直 2–4 像素/秒。现版的 6.5 像素/秒加上等距排队，读起来像"行军"。

### 5.3 实现：解析轨迹 + 整数像素（推荐 `_draw()`）

建议放在原生分辨率的 SubViewport 里，用 `Node2D._draw()` 画，每帧不到 300 个矩形，开销可以忽略。

- 位置是 `(i, t)` 的纯函数：可重现，录屏验收和过场回放都是同一画面。
- 像素坐标取整：不会糊，也不会抖。

用 `GPUParticles2D` 的话，要写 `shader_type particles;` 的 `process()`，按同一公式算位置并取整。`ParticleProcessMaterial` 和 `CPUParticles2D` 的现成参数（重力、轨道速度、径向加速度、湍流）只能做出圆锥或喷泉，做不出"窄相位带来的腰"，不推荐。

```gdscript
extends Node2D
# 「倒置沙漏」灯流：v0.1 的原版公式，默认参数取 5.2 的推荐值（v0.1 原值：traverse 55.6、bow 14、amp 9.6）。
# 坐标是原生像素，y 向下。时间由过场时钟给（不要用墙钟），方便重现。
@export var n := 90
@export var traverse_s := 50.0
@export var base := Vector2(289, 134)       # 起点：地平线下 6 像素
@export var travel := Vector2(-96, -125)    # 起点到终点
@export var bow := 12.0                     # 中段上弓
@export var amp := 12.0                     # 横向摆幅 A
@export var omega := 3.0
@export var phase_span := 1.0               # 决定腰的粗细与高度
var t := 0.0
var ph := PackedFloat32Array()
const C1 := Color8(255, 138, 70)
const C2 := Color8(255, 176, 112)
const HEAD := Color8(255, 224, 176)

func _ready() -> void:
	var rng := RandomNumberGenerator.new()
	rng.seed = 42
	ph.resize(n)
	for i in n:
		ph[i] = rng.randf()

func advance(dt: float) -> void:          # 由过场调用
	t += dt
	queue_redraw()

func _draw() -> void:
	for i in n:
		var p := fposmod(float(i) / n + t / traverse_s, 1.0)
		var x := base.x + travel.x * p + amp * sin(omega * p + phase_span * ph[i])
		var y := base.y + travel.y * p - bow * sin(PI * p)
		var a := clampf(p * 6.0, 0.0, 1.0) * clampf((1.0 - p) * 3.0, 0.0, 1.0) * (0.75 + 0.25 * sin(t * 6.0 + ph[i] * 20.0))
		if a < 0.03:
			continue
		var c: Color = C1 if ph[i] < 0.5 else C2
		c.a = a
		draw_rect(Rect2(floorf(x), floorf(y), 1, 2), c)
		if ph[i] < 0.3:
			var h := HEAD
			h.a = a
			draw_rect(Rect2(floorf(x), floorf(y) - 1, 1, 1), h)
```

光晕另放一个 `CanvasItemMaterial.blend_mode = BLEND_MODE_ADD` 的子节点。在每个点上画一张 5×5 的阶梯光晕贴图，调制透明度约 0.25 × a。

### 5.4 叙事版：平原上的灯各自离开，再汇成沙漏

新剧本要的是"平原上的万家灯火往上汇聚"，而 v0.1 的灯是从一个点冒出来的。把两者接起来的做法：

- **出发**：从城镇及周围（半径约 40–70 像素）的真实灯位里抽取出发点 `S_i`。每盏灯只离开一次，离开时地面上那盏灯熄掉。出发时刻用泊松过程，平均间隔 0.3–0.6 秒，随 `rise` 加快。**不要按地方排队。**
- **寿命**：每个点 `T_i = T · U(0.85, 1.15)`，相位 `φ_i ~ U(0,1)`。
- **位置**：先算 5.3 的 `plume(p)`，起点放在城镇上方的地平线附近；再算聚拢权重 `g(p) = smoothstep(0, 0.25, p)`。
  ```
  pos = lerp(S_i + Vector2(0, −8·p/0.25), plume(p), g(p))
  ```
  也就是先从自己的灯位直直往上升一点，再被吸进那股流里。
  - 这样，腰以下自然形成一个由各处的点收拢而成的漏斗，也就是沙漏的下半；
  - 腰以上仍是 v0.1 的散开和渐出；
  - 抵达门口前淡出，门口的光随抵达的数量变亮（现版的做法可以保留）。
- **别加回去的东西**：
  - 每地一条的固定路径；
  - 等间隔放灯；
  - 拖尾；
  - 竖直光柱；
  - 左右对称的分道。

### 5.5 先做哪个

用户点名的是"一开始那种感觉"，所以默认按 5.3 的原版参数实现，起点放在城镇上方。5.4 的聚拢是可选项：要不要加，在下一次提案或交付说明里请用户定（P-1：不为此单独发试看版）。两版都要过 5.1 的验收。

## 6. 怎么验收（可重做）

1. 用过场时钟以固定步长渲染这段远景，每 0.1–0.2 秒存一帧原生画面，取 10–20 秒。再渲染一张同时刻、没有升灯的底图。
2. 每帧减去底图，只留"红通道增量 > 40 且 R ≥ B"的像素。对所有帧取逐像素最大值，就是长曝光图。
3. 逐行量：
   - 被点亮的列数；
   - 最左到最右的跨度；
   - 分成几段（相邻点亮列的间距大于 2 像素就算分段）。
4. 合格标准：
   - 流经的每一行只有 1 段（最底部汇入处除外）；
   - 跨度呈 宽 → 窄 → 宽；
   - 单帧里看不到任何连接两点的像素。

## 7. Godot 版（2026-10-14）：怎么实现、提升了什么、怎么验收的

> 代码在 `godot/vista/`（场景、脚本、着色器、数据），生成器在 `tools/vista/`。重建数据只要一条命令：`node tools/vista/bake.mjs`（约 10 秒，确定性的：同一份代码重跑，产物逐字节相同）。预览和检查图在会话草稿目录 `vista-godot/`，不入库。

### 7.1 结构

- 入口是 `Vista`（`vista.gd`，一个 Control）。它有自己的 HDR 子视口（原生分辨率，四周各多 1 像素，RGBA16F），最后由 `display.gdshader` 转回 sRGB，加暗角和远之浪终段的白，再按舞台的整数倍显示。共三个镜头：
  - `south`：序章树顶南望（`south.gd`、`south_lights.gd`、`south_wave.gd`）；
  - `tower`：「隔」塔的插入镜头（`tower.gd`）；
  - `title`：标题背景，只有画面，菜单归核心（`title.gd`）。
- **画面内容全部来自 HEAD 的 JS 生成器，没有重画。**
  - `tools/vista/bake.mjs` 在无头 Chromium 里运行 HEAD 的生成器（`src/vista/` 的天、地面、建筑、树、浪、时刻）。`tools/vista/bake/south.js`、`title.js`、`tower.js` 按 HEAD 各镜头的顺序调用它们，只是画在更大的画布上，并把结果拆成图层导出。生成器本身只复制改了一个：`tools/vista/bake/skyshore.js` 多了一个参数，让天岸能画在更宽的画布上。
  - 导出的是"索引图层 + 每个时刻的调色板行"：17.0–21.5 时，每 0.05 时一行，共 91 行。再由 Godot（`tools/vista/pack.gd`）打包成 `godot/vista/data/*.res`，共 2.7 MB。
  - 着色器在相邻两行调色板之间插值，所以黄昏到夜是连续的。JS 是每 0.05 时跳一档。
- **升灯的规划**（每盏灯的轮次、时长、控制点）用 `8196ebf` 的代码原样计算，逐行搬进 `tools/vista/bake/south.js`，落在 HEAD 的平原和灯位上。
- **改了烘焙的编码，就要重烘并把 `godot/vista/data` 一起提交。** 本次就发现入库的 `south_deck.res` 还是旧编码，着色器按新编码读，云层的密度被读成了 2/3；已经重烘。
- **核对用的数据**：`node tools/vista/bake.mjs --canon DIR` 另出一套与 JS 480×270 完全同参数的数据。配合 `Vista.exact = true`（调色板按 JS 跳档，地面的灯按 JS 瞬间熄灭），可以与 JS 逐像素对照。

### 7.2 画面尺寸与构图

参考帧是 JS 的 480×270。舞台按整数倍填满窗口，逻辑画布随窗口变大：1280×720 → 640×360，1200×540 → 600×270，1920×1080 → 480×270。远景的做法是看到同一个世界的更多部分，不放大，不留黑边。

- **远景组**（天、天岸、云、平原）：按 JS 的地平线公式定位。画布向四周预留了余量：宽 1024，地平线以上 440 行，以下 200 行。
- **天岸**：JS 里它随画面高度缩放。这里按 270、360、450 三档高度各烘焙一份，选地平线放得下的最高一档；超出那一档的高度，天岸在上方渐隐。
- **树冠**：向两侧和上方补了叶簇。参考帧里的叶簇与 JS 完全相同，只在帧外补画；她坐的枝、站的位置不变。
- **近景叶**（摇臂上升时从镜头前滑过的叶枝）：JS 按画面高度排布它们。在 640×360 上，摇臂起点时这几簇会悬在天空里。现在改为：起点时它们与树冠的相对位置和参考帧相同，相对行程同样是 150 像素。480×270 时与 JS 逐像素相同。
- **塔和标题**：主体保持 JS 帧里离画面底部的距离，居中。悬在上方的东西（标题的树冠和月亮、塔后天岸的残影）挂在画面顶部；画框边的叶子贴在各自的角上。
- 测试 `test_every_logical_size_is_covered_and_keeps_its_landmarks` 检查 7 种逻辑尺寸，三项都要满足：
  - 画布盖满画面；
  - 门口和她的枝都在画面里；
  - 天岸的档位放得下。

**注意：用户的两张参照截图不是 480×270。** 它们是 JS 在 1280×720 窗口里按 3 倍显示的 427×240 画面；`8196ebf` 在 427×240 下渲染，与截图的平均差只有 3/255。Godot 的舞台在同一个窗口里是 2 倍、640×360，所以同一个窗口里，灯流在画面里约小三分之一。1920×1080 窗口下是 480×270（4 倍），与参照的取景接近。要不要让远景在大窗口下按更大的倍数显示，是舞台层面的决定，这次没有改。

### 7.3 升灯：`8196ebf` 原样移植

- **轨迹**：每盏灯一条三次贝塞尔曲线：灯位 → 所在地方上方的聚集点 → 门口与地方之间 → 门口 ±1.5 像素。
- **时长与速度**：7.4–9.9 秒走完；两盏独行的灯 11 秒。进度曲线 `s = u·0.62 + smoothstep(u)·0.38`；独行灯是 `u·0.85 + u²·0.15`。
- **颜色**：本岸的暖色在路程过半后渐变成天岸的淡翡翠色。
- **呈现**：
  - 核 1 像素，火和独行灯是 2×2；
  - 阶梯光晕，半径 2、4、6；
  - 尾巴沿灯自己的曲线，1、3、8 节；
  - 云未开时，快到门口的灯被云吞掉。
- **出发**：`rise` 跨过一盏灯的轮次 r 时，这盏灯出发。`rise` 跳变时，出发时刻按 JS 的规则补算：`t − (rise − r)·30`。所以跳到任意时刻，和连续播放到那一刻是同一个画面。`rise` 倒退时灯回到地面，这是给编辑和测试用的。
- **计算放在哪里**：位置和外观都在 GPU 的顶点着色器里算（`shaders/rise.gdshader`）。一个实例 = 一盏灯的核与光晕，或者一节尾巴。CPU 只记两样：出发时刻（一行浮点纹理）和抵达。
- **像素**：核和尾巴都落在整像素上，与 JS 的 `Math.round` 一样；时间是连续的。
- **数量**：南望画布上共 616 盏灯。参考帧内 591 盏，与 JS 相同；多出的 25 盏是帧外稻田里的星影。

### 7.4 新引擎里的提升（"聚向一点"的形状不变）

1. **HDR 光晕只给光源。**
   - 远景在 HDR 视口里画，画出来的颜色都不超过 1。灯核额外加一截超过 1 的亮度，辉光阈值设为 1.0。所以只有灯、火、门口和塔灯会泛光，云和地面不会发灰。
   - 灯的叠加在三个 sRGB 单位的光缓冲里进行，等同于 JS 的 AddBuffer：天岸、地面的灯、升灯各一个（`vista_light_buffer.gd`、`composite.gdshader`）。
   - 每个缓冲各自决定有多少溢出变成泛光（0.6 / 0.06 / 0.45），所以城镇不会糊成一团。
2. **门口随抵达一亮一亮。**
   - 保留 `8196ebf` 的做法：门口亮度 = 1.5 秒内的抵达数 ÷ 12。
   - 另外每盏灯进门时加一下闪，0.28 秒衰减。
   - 云未开时，这些闪从云底透出暖光。云底的暖光也随空中的灯数变化，与 `8196ebf` 相同。
3. **灯离开地面时有过渡。**
   - JS 里地面的灯在出发那一刻直接熄灭。现在离地时先亮一下（0.07 秒），再在 0.55 秒内熄灭，同时上方的火星渐入。
   - 火堆留下余烬，直到远之浪到达。
4. **桌面版有更多的火星**（quality "high"）。
   - 伴随火星：篝火的每盏光带 4 颗，火的每盏光带 2 颗，约一半的窗和灯笼各带 1 颗。
   - 它们比本灯晚 0.1–1.3 秒出发，各自沿抖动过的曲线走；单像素，无尾巴，稍暗。
   - 光点从 616 增到 947。"low"（手机）只用 JS 原有的 616 盏。
5. **质量开关**：`Vista.quality`，取值 "auto"、"high"、"low"。"auto" 在安卓和移动端是 low，其余是 high；命令行可用 `--vista-quality=low|high`。low 还把远之浪的光尘从 1600/900 降到 700/400。

### 7.5 时间线 API（台词不写死）

- **分拍函数**：`begin()`、`crane_up()`、`first_light()`、`lights_leave()`、`sky_opens()`、`tower_goes_dark()`、`far_spreads()`、`set_pose()`、`far_arrives()`。它们都在导演（`Director`）的游戏时钟上 await。
- **整段**：`play_prologue(director, between)` 按 JS 第一段的顺序和时长把它们串起来，共 65.6 秒。
- **停顿与台词**：四个停顿是 plain 5.7 秒、first_light 1.5 秒、sky_shore 4.5 秒、far 2.6 秒，台词由宿主在 `between(name, seconds)` 里放。
- **信号**：每一拍发出 `beat(name)`。
- **宿主怎么接**：
  - 把 `Vista` 放在一个 CanvasLayer 上：在世界之上，在演出层（黑边、淡入淡出）和文字层之下；播放时把世界藏起来。
  - `figure_slot()` 是放她的精灵的节点，夹在她身后的树冠和身前的叶子之间。
  - `anchors()` 给出 `branch`（坐处）和 `stand`（站处）。
  - 导演控制时钟时（跳过、暂停），设 `autoplay = false`，每帧调用 `advance(dt)`。

### 7.8 已知不足

- 树冠在参考帧外补的部分，画法与 JS 相同，但 JS 本来没有这些像素，所以无法逐像素对照。
- 天岸显现过程中的半透明是在线性空间里混合的；JS 是在 sRGB 里混合，所以显现到一半时明暗略有差别。全开后与 JS 的差别只剩动画的相位（天岸上的灯、门口的脉动、树冠边的叶）和远缘的一行像素。月晕和塔后天岸的残影在 sRGB 里叠加，与 JS 相同。
- 伴随火星、门口的闪、地面灯离开时的过渡，都是新加的。泛光的强度只在软件渲染器上调过，没有在真机上看过。
- 塔和标题是固定时刻（21 时），不随时间变化，与 JS 相同。
- 摇臂上升时，远景组按 0.1 倍视差、以整像素步进。慢的时候约每 6 帧移 1 像素，与 JS 相同，没有做子像素平滑。

### 7.9 G5R2-4 的三个 bug（2026-10-15 修）

用户看过的是 `review6` 页里的录像（1280×720 窗口，426×240 ×3，Mobile 渲染器）。下面"修前"的数字都是在那段录像的帧上量的（降回原生像素）。检查脚本在会话草稿 `vista4/tools/`（`nearcheck.py`、`final_checks.py`、`glints.py`），回归测试在 `godot/tests/test_vista.gd`。**与 JS 逐像素对照（canon + exact）从此在这三处不再相同，是有意的。**

**① 升镜时悬空的树枝：素材本身没有连接，视差把它暴露出来。**

- 是哪些枝：近景叶层（`nearLeaves`，视差 2.4）。HEAD 的 7 簇加上宽画布补的 6 簇，每簇是一根 40–80 像素长、5 个点的小枝（粗端半径 3）挂 4 团暗叶。**粗端就停在半空**，什么也没接上。摇臂上升时这一层比树冠快 2.4 倍往下滑，所以读成一根根带断口的枝在树冠前面飘；480×270 上有的叶簇还伸进树冠线以上的天空。不是视差层错位，也不是裁切：JS HEAD 就是这样。
- 量法：按 `VistaSouth.update()` 的公式把近景层放进画面，摇臂 0–1 取 101 步，把画面里的近景像素按 8 邻接分块；既不碰画面底边也不碰左右边的块就是"悬空"。修前 17 种画面尺寸（各种窗口按 round(h/270) 得到的画布）全部有：40–69% 的帧里至少一块悬空，1024×560 同时最多 19 块。
- 改法（`tools/vista/bake/south.js` 的 `nearLeaves`）：每根小枝从粗端接着长出它所属的枝：沿小枝自己的方向往回、向下弯、由 3 像素渐粗到约 6.5 像素，一直伸出层的底边；末端相距 70 像素以内的枝在下面并成一根（分叉）；枝上每隔 24–34 像素在两侧交替长一根带一小团暗叶的侧枝。层加高到 REF_H + 190 = 460 行（叶簇仍按 JS 的 310 行排），所以 600 行以内的任何画面，摇臂全程层的底边都在画面下方；小于 6 像素的孤立碎点去掉。原来的叶簇位置、形状不变（28 995 个像素里 27 184 个完全相同，其余是新枝旁的接触阴影和亮边）；树冠、摇动的叶、调色表都没变。
- 修后：同样的检查 17 种尺寸全部 0 块悬空；近景层在任何尺寸、任何时刻都不盖住她（她的精灵框里 0 像素）。测试 `test_the_near_leaves_hang_from_branches_below_the_frame`：近景层每个不透明像素都能从它的底行连通到；8 种尺寸、摇臂 0–0.75 时层的底边都在画面下方。

**② 天岸的水流方向：反了。依据是天岸自己的地势。**

- 天岸上会动的水只有河上的闪光（`shorelights.gdshader` 类型 1），没有画瀑布。三条河各是一条折线，从天门脚下（u = 0）一直通到它远处的山（u 约 100），画得出来的点带着 u。亮度是 `sin(0.9u − 1.6t + 2.1i)` 超过 0.82 的部分：波峰以 1.78 单位/秒往 u 增大的方向走，也就是离开天门。天岸是倒挂的顶，近处投影得高，所以天门那一端在画面上方：闪光往**下**走，和我们这边的水落下的方向一样。修前在用户的录像上量到 +1.8 u/秒、每秒往下 2.1–2.7 行。JS 的注释写着"闪光沿河往上、离开天门：它们的水和我们的反着流"，本意是"相反"，但"离开我们"在画面上恰好是往下。
- 天岸的地势：`depth(X, Z)` 是它的地面从基准面往下（朝我们）垂了多少。它的重力朝上（背离我们），所以垂得越多的地方对它来说越高。沿三条河画出来的那一段，depth 从天门那头的 0.06–0.17（天门下的低地）升到远端的 2.6–7.5（它的山），三条河在三个高度档里线性拟合的斜率都是正的（每单位 u +0.04 到 +0.11）。所以它的水从山上流下低地，流向天门，u 减小：**从我们这边看是往上**，朝它的地面那一侧。我们这边的河灯往我们这边漂（画面上往下），天岸正好相反。
- 局部：中段那条丘陵带（Z 43–63）里河床高低不平（JS 只把河谷挖了 0.09–0.63），那几段大多被丘陵挡住，看不见；这次没有重挖地形（会改天岸的画）。
- 改法：`sin(0.9u + 1.6t + 2.1i)`，同样的速度，波峰往 u = 0 走。修后在帧上量到 −1.5 到 −1.95 u/秒、每秒往上 2.3–2.7 行。测试 `test_the_sky_shore_rivers_run_from_the_gate_out_to_its_far_ranges`（数据里每条河都是天门那头在上，着色器的方向是往 u = 0）。

**③ 遠化时她向右跳：站处和坐处不是同一个点。**

- 原因：`VistaSouth.update()` 坐着时把她放在 `anchors.branch`，站、喊时放在 `anchors.stand`。烘焙按 HEAD 把坐处放在 0.62 W、站处放在 0.69 W（JS 的 `stage.js` 也是这样），中间没有任何过渡，所以 t = 60.0 秒她站起来时一帧之内右移 33 个原生像素（1280×720 上约 100 个窗口像素）。不是换帧时锚点不一致（她背面的坐、起身、喊每一帧枢轴都是 (32, 58)，水平范围都是 17–48，起身第一帧和坐姿逐像素相同），也不是相机取整（摇臂结束后树冠不再动）。修前在用户的录像上按她的精灵帧逐帧匹配：脚点 x 在 t = 60.23 秒从 271 跳到 304，正好是 sitEdge0 → standUp0。
- 改法：站处就是坐处（烘焙里 `sx = bx`）。她在原地站起来（起身 → 喊）。
- 修后：1280×720 和 1920×1080 两段新录像里，她的脚点在任何相邻两帧之间横向移动都是 0 像素（只有摇臂时每帧 1–2 像素的竖向移动）；站起、喊的那几帧 x 不变（426×240 上 271，480×270 上 298）。测试 `test_she_stands_up_where_she_sat`。

**④ 渲染器改成 Forward+ 之后的泛光（同日）**

**③ 远山：压了多少、为什么**

- 主管定："远山的轮廓照 3D 描，同方位、同形状。高度先照 3D 的比例；只有当山顶会顶进'天岸显出来'那一层云时才压，压到刚好不碰就停。"
- 照 3D 的仰角，16:9 画框里最高的峰（11 km 外）在地平线上 38.5 像素；天岸显出来时，它下面那层雾带最低的可见行在地平线上 22 像素（270 档。360、450 档是 46、76 像素，但按 round(h/270) 的画布，常见窗口都用 270 档）。所以地平线以上统一乘 **0.52**：最高 20 像素，离雾带留 2 像素。地平线以下（平原）不动，形状和方位不变。
- 比 533 像素更宽的画布（21:9 的 3440×1440 是 688 宽，32:9 是 960–1024 宽）两侧还看得到更近更高的山（最高 55.7 像素）。那里的系数按列算：先取每列"刚好不碰"需要的值，从中间往外取累计最小，再腐蚀、平均（各 24 列），所以平滑、而且每一列都不碰；左边降到 0.36，右边 0.39。16:9、16:10 和 2560×1080 的画面里全是 0.52。
- 顺带：平原的俯角本来就是 0.48 倍，山乘 0.52 后，山和平原的上下比例几乎一致，和 3D 里山与平原的相对高低相同。
- 代码是 `plain.js` 的 `mountainFit()`；数值写进 `south.json` 的 `meta.mountain`。

**⑤ 遠化的"褪版"（G5R3-18，同日）——试过、被否（G5R3-22），代码已删**

> **被否的原因**（用户 G5R3-22 原话的意思）：①**位置不对**：褪版按离区边缘的距离分档，看起来是"远山那一边的一条带"，和爬上树以后那段动画对不上——动画里潮是在平原差不多中心的位置像原爆点一样爆开的；②**看起来脏、像灰模**："现在这种看上去有点太脏了，整个画面感觉很脏，跟美术的感觉不是很协调，就像个灰模一样"。用户反而点名要回到 0.2 版那种"幽灵一样银白色"的遠化。另外主管认了自己的错：G5R3-15 用户说的是眺望里遠化的位置不对、没表现好，主管把它推广成"不能用变白"，连序章原来的银白也改掉了。
> **教训**：①遠化的"在哪里"是剧情事件定的（潮从町爆开），画法不能另起一套地理；②把整片地压成纸和墨线（大量一两像素的线、中性偏褐的灰），在柔和的夜景里读成"潦草的速写贴在画上"，即使线是按刻版规则画的；③用户说"不要像雾、变淡"的时候，先问清是位置问题还是画法问题，不要把一个具体的批评推广成一条禁令。
> 下面是当时的做法，留作记录（代码在快照 `4000176` 及以前的 `tools/vista/bake/plain.js` 的 `fadeMaps()`；现在的做法见 ⑦）。


- 用户批准的画法：遠化的地像一张色版被一块块揭掉的浮世绘。先掉晕染，再掉绿，再掉水的蓝，再掉土色，最后只剩墨线和空摺的纸白；东西始终看得清，不被雾遮；遠化区里不动、水不反光；夜里没有灯。序章里白潮扫过的那一刻照旧是一道白（事件本身），潮过之后的平原是褪版。第四轮及以前，潮过之后整片地换成一种固定的淡蓝灰（`ghost()`），正是被否定的"雾、变淡、变白"。
- 第一版按夜的光照把纸压暗（深蓝灰、线也淡），主管看了说读起来是"变暗了、像关了灯"，不是"掉了版"。改成下面这样（主管的四条：纸要读得出是纸；墨线是全画面最清楚的东西；掉版有边；空摺只在大的起伏上、不碎）。3D 眺望（`vista_common.gdshaderinc` 的"褪版"）照同样的四条定，两处一套。
- 烘焙（`tools/vista/bake/plain.js` 末尾）：
  - 每种地面材质属于一块版、一个色调：稻田、草地、田埂 = 绿版亮；林、杉、屋敷林、远山的林 = 绿版暗；河、池、水田 = 水版；旱田、休耕地、路、町的地面、岩、河堤、茅草和亮屋顶 = 土版亮；暗屋顶、木、高架桥 = 土版暗；白墙、仓 = 纸。
  - 第 1 档起去掉晕染：每块版平涂成一个色调（用夜里这个材质在平地、开阔天空、无雾时的颜色：绿亮 = 稻田、绿暗 = 林、土亮 = 休耕地、土暗 = 木；水版是水当时映的天、平涂）。版掉了（绿在第 2 档、蓝在第 3 档、土在第 4 档）或本来是白的，就是纸。
  - **纸**：夜里月光下没上墨的和纸，比旁边带色的夜景亮一档，平、匀；第二版的中性灰 (76, 76, 75) 挨着蓝夜读起来是脏的褐灰（主管第三次意见），往冷挪到 sRGB **(73, 77, 87)**（亮度不变，约 L\* 32）。不按夜的光照压暗。`lutFar` 里纸的那一格用 alpha 128 作记号（`lutRows` 的 `keepAlpha`），着色器只给纸加空摺和纸纹。
  - **纸纹**：纤维的长短斑（一层 7×1.6 像素的长斑、一层 2.2×1.4 的短斑），±2.5%，按画布坐标固定（画布随地整像素移动，所以跟着地走、不随镜头抖）；远山上减到 35%，让起伏的明暗读得出来。
  - **墨**：近黑、带一点调色板里墨 K 的暖：(15, 13, 13)，二值，全画面最清楚的东西。第二版的线是逐像素找边，平原上全是一两像素的碎线（主管："主版的线是有意画的、连贯的"）。第三版按刻版的方式画：
    - 主线（约 1.6 km 以内 2 像素：线和它下面一格，停住那一帧里树冠以上看得见的近处平原就在这一段；再远 1 像素；桥面自己就是两行，不再加）：天际线；远山一道道的山脊（见下）；地形的坎（"后面的地比这里远出一截"）；高架桥的桥面（近处两行都画，约 1.5 km 以内长于 5 像素的桥墩才画，短的会印成梳子；色版也不刻桥墩：版还在的地方，没画墨线的桥墩印成纸）；河岸、池岸、路（约 2.9 km 以内）、町的轮廓。

**⑦ 遠化：银白的幽灵，以町为原爆点（G5R3-22，取代 ⑤）**

用户原话："我覺得這個演化的場景的位置完全不對，他不應該是遠處的山那一邊……那個動畫是在平原的差不多中心位置像一個原爆點一樣爆開而且我希望遠化能夠多一些還是蜃樓一樣的感覺或者粒子效果，你一開始做的那個應該是 V 0.2 版本吧……就是幽靈一樣銀白色的。我感覺那個還不錯"。主管的要求：照 0.2 版 `ghost()`，田、路、屋顶的明暗留住、形状清楚；以町为原爆点，町一带最银白，往外留一点颜色；蜃楼和粒子要克制；**原爆点和分圈和 3D 眺望是同一套**。

- **位置和分圈**（`tools/vista/bake/plain.js` 的 `ghostK`，逐行移植自 3D 的 `godot/world3d/vista3d.gd` `ghost_k` / `vista_common` 的 `v_ghost_k`）：原爆点是町（`vista.json` 户数最多的村，(−260, 2160) m，离树冠 2.2 km）；离町 400 m 以内 1，1,100 m 处 0.75，2,600 m 处 0.4，5,500 m 以外 0，圈间 smoothstep；每圈半径随方位起伏 ±10%（同一个 `w3_hash` 值噪声、同样的参数）；区的雾椭圆（cx −50、cz 100、rx 430、rz 370 m）1.15 倍以内不受影响、到 1.8 倍渐入，所以树冠下的下层（溜池、梯田、农家）和眺望一样不变。烘成每个地面像素一个 k（`south_groundGhost.res` 的 R；G = k^1.5，蜃楼的幅度）；数在 `south.json` 的 `meta.ghost`。3D 改了数要在 `to_vista2d.md` 说，序章改 `GHOST_R` 重烘（约 15 秒）。
- **画法**（`plain.js` 的 `GHOST_LOOKS` 和 `ghostPalette(look)`）：照 0.2 版 `ghost()`："everything is still there, fields, roads and roofs keep their own lightness, but drained of colour, lifted and blue-grey, lit by nothing in particular"。按材质的反照率和烘焙的受光档、天光档算亮度 l（显示空间，"不知哪来的中等光"），所以**不随时刻的光变**：夜里也是它自己的光，比周围的夜亮。两种样子：
  - **银灰（`grey`，夜里用；序章全程是夜，整段都用它）**：0.2 版的亮度拉开约三成，l → 0.2 + 0.74 l^0.85；颜色 = 亮度 × 冷银 (0.86, 0.92, 1.07)，再和自己的颜色按一成混；雾只留 0.2 版的一半。田、路、屋顶的明暗和形状清楚；高架桥是暗的灰褐一线。
  - **银白（`white`，留给 3D 白天可能用）**：3D `v_ghost` 的曲线 l → 0.34 + 0.6 l^0.8，冷银白 (0.88, 0.93, 1.05)，同亮度留一成自己的颜色。
  - 经过：第一版（v6）是银灰；主管要"银白，不要银灰"，v7 换成银白（町一带 sRGB 约 135–170）；用户看了 v7（G5R3-26）："我感覺覺得之前的銀灰色在夜間的表現還是不錯的，你現在改成銀白色在晚上感覺就有點太亮了，不是很合適"。所以**夜里用银灰**，序章退回 v6（烘焙结果和 v6 逐字节相同，只多了 `meta.ghost.look`）。3D 夜里照同一组数（`coord/to_renderer.md`）。
- **混法**（`godot/vista/shaders/ground.gdshader`）：潮头两格照旧是白（事件本身）；潮过之后每个像素在**线性光**里 mix(夜里的原色, 幽灵色, k)（和 3D 一样；在 sRGB 里混，中间那几圈会更暗、更灰）。结果：町一带 sRGB 约 110–150，两侧约 55–90，往远处渐暗到夜色，5.5 km 以外和远山照旧；树冠下的下层照旧。
- **灯**：照 3D 的 `v_drain`（smoothstep(0.2, 0.35, k)）：潮过时 k 高处的灯灭，过渡段按每盏灯自己的抽签（`plain.js` 的 `lampDrained`，`south.js` 把不灭的灯的 arr 写成 9）；离町约 3.5 km 以外和区里的灯不灭。910 盏里 240 盏不灭，大多在潮来之前已经升走，停帧里只在地平线附近剩几点。
- **蜃楼**（`ground.gdshader`）：照 3D `vista_post` 的式子：n = 0.6 sin(x/11 + 0.7t + 1.6 sin(y/5 + 0.9t)) + 0.4 sin(x/29 − y/13 + 0.45t)，坐标先乘 4/3（序章的像素在 1080p 是 4 个屏幕像素，3D 是 3 个，所以带子在屏幕上一样大），偏移 = round(1.15 · k^1.5 · n)：只有 −1、0、1 一个整像素，成片地动、往上漂；k 0.5 以下几乎没有；只从遠化自己的地（k > 0.05、潮已过）上取，近处的地不会滑进来。
- **光点**（`godot/vista/south_wave.gd` 的 `_spawn_ghost`、`motes.gdshader` 的 ghost 模式；照 3D 的 `_motes`）：最多 220（低画质 110）；每秒 n/9 次、每次最多 8 试，在町周围 5.5 km 内均匀取点、按 k³ 接受（所以大多在町上空），只在看得见、潮已过的地上生；离地 1–24 m，每秒升 4.5–10 m（序章里每秒约 0.8–1.7 个原生像素），到寿命末减到 0.6，横向 ±1.2 m/s 加慢摆；活 6–12 秒，淡入前五分之一、淡出后五分之二；一像素，一成两像素，整像素落位；夜里 0.7 × 0.8–1.15。直接进停帧（不是从潮演过来的）时，第一帧先按各种年龄放满。潮到树冠时前景的光点（`endmotes`）照旧。
- **停帧**（`Vista.play_standalone()`、`settled`）：白退去以后停在遠化留下的平原上：町一带银白、有光点升起、空气微颤，往外渐回夜色，天岸在上，她站在枝上。
- 验收（本次实测）：`ghostprev.py`（会话草稿：从原始烘焙合成停帧的地面和 k 图）；Godot 实际截图 w20 / w45 / w70 / settled（Forward+、Xvfb + Mesa）；停帧连续 9 帧（每 0.5 秒）比较：蜃楼只在町一带移动边缘一个像素，光点每秒升一两个像素、町上空最密；`test_vista` 9 项通过。
- 删掉的：褪版的 `fadeMaps`、`groundFade` 图、`lutFar` 第 2–4 行（现在两行：0 潮头的白，1 幽灵色）。
